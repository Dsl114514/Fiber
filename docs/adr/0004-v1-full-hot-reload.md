# v1 支持全热重载(文件监视 + 自动重载)

用户否决了"v1 静态加载"的保守方案,明确 v1 就要全热重载:监视 mods\ 下 DLL 与清单文件变化,自动重载 Mod。理由:用户本人即主要 Mod 开发者,改代码→编译→自动生效的开发循环是核心体验,不是锦上添花。

此决策与既有决策的交互(设计上已消化):

- **与 ADR 0003(主线程分发)相容且互相成全**:卸载流程 = 静默期(quiesce)—— 停止派发 → 排空事件队列 → 等待在途回调返回 → 调 Fiber_OnUnload → 注销该 modid 全部订阅 → FreeLibrary。全部在主线程完成,无并发窗口。
- **与 ADR 0002(多入口契约)相容**:Fiber_OnUnload 本就是为干净卸载设计的;热重载复用同一契约。
- **与总线架构相容**:Mod 只订阅、不持有 hook(内核 hook 为全局所有),卸载 Mod 永不触碰蹦床,FreeLibrary 无悬挂执行风险。
- **Windows DLL 锁问题**:Runtime 一律从**影子副本**加载(shadow copy,加载前把 mods\<modid>\*.dll 复制到缓存目录再 LoadLibrary),源文件永不被锁,编译器可随时覆盖输出。
- **与 Q14(SEH 自动禁用)的组合语义**:Mod 被自动禁用后,源文件变化触发成功重载 → 禁用状态清除,重新以全新状态加载。

# Considered Options
- v1 静态加载(被否决):实现最稳,但用户明确要开发循环优先。
- v1 支持启停不换文件:半吊子方案,仍要处理全套卸载语义却省不了多少。

# Consequences
- 热重载进入 v1 关键路径,事件总线必须从一开始就支持按 modid 完整注销。
- 状态保持明确不做:每次重载 = 全新状态,不序列化 Mod 内存状态(v1 范围)。
- 文件监视、防抖、重载失败语义另行决策(见 CONTEXT 开放问题)。
